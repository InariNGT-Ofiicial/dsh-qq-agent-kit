# DSH 接入 QQ 与上云部署：四路线可复用指南

版本：2026-10-27 本地接入验证版。用途：从新环境建立 QQ ↔ DSH 的最小消息闭环，并按需迁移到云端。

本指南只保留接入、权限、运行、迁移和验收。角色设定、职务、业务任务、旧聊天记录、全量群消息归档与文件同步均不作为接入前置条件。

**验证状态**：R1 已实际登录指定个人小号，OneBot 身份/在线状态正确，隔离 DSH 也已实际返回“DSH本机测试通过”，受限预设可见工具数为0；私聊配对已成功，修复后已补处理一条真实消息，QQ发送成功且历史出现回复；仍需新消息验证实时监听。R4 已找回原 SSH 连接并完成只读预检，尚未部署个人号实例。官方 Bot 路线仍只有原工程历史实测与本轮文档/源码复核。各段通过不等于四条路线全部通过。

## 1. 先选身份，再选运行位置

| QQ 身份 | 本地运行 | 云端运行 |
|---|---|---|
| 个人 QQ 小号：程序使用该账号收发消息 | **R1 · DSH–QQ 号本地接入** | **R4 · DSH–QQ 号上云部署** |
| QQ 开放平台的独立机器人身份 | **R2 · DSH–QQ Bot 本地接入** | **R3 · DSH–QQ Bot 上云部署** |

“个人 QQ 号接入”在这里明确指程序代登录自己的小号，不指用手机 QQ 扫码授权一个官方 Bot。两者都可能出现二维码，但二维码授予的身份不同。

| 对比项 | R1 / R4：个人号 | R2 / R3：官方 Bot |
|---|---|---|
| QQ 中发言的身份 | 登录的小号 | 独立 Bot |
| 接入链路 | QQ 客户端或协议端 → OneBot 等接口 → DSH 桥接 → DSH | QQ Bot API → `@tencent-connect/dsh-qqbot` → DSH |
| QQ 侧凭据 | 登录态、协议端访问令牌 | Bot AppID / AppSecret |
| DSH 侧凭据 | 桥接访问 DSH 的鉴权 + 模型凭据 | 模型凭据 |
| 联系人标识 | 按桥接字段使用 QQ 号、群号或对应标识 | user openid / group openid |
| 上云额外工作 | QQ 客户端/协议端、登录态、桥接、DSH 一起适配 | 插件与 DSH 托管，重配路径和凭据 |
| 关键区别 | 第三方个人号接入，不承诺免风控或永久在线 | 官方 Bot 接口，不接管个人号 |

个人号采用“协议端 + DSH 桥接”的结构。本轮实际选择 **NapCat + 本仓库最小私聊桥接 + DSH**；只复用了 `qq-bridge` 的 MIT DSH 客户端，没有运行其完整仿真桥接或 SnowLuma。不能把这次组件验证等同于完整上游桥接与 NapCat 已兼容。[NapCat 文档](https://napneko.github.io/guide/napcat)、[qq-bridge 项目](https://github.com/Derpyu520/qq-bridge)。

## 2. 所有路线共用的最小目标

第一阶段只做：**一个允许使用的人，在私聊里发一条消息，DSH 处理后，回复返回原会话。** 群聊和工具执行分别追加验收。

开始前记录以下信息：

| 参数 | 记录内容 |
|---|---|
| 路线 | R1 / R2 / R3 / R4 |
| 系统与架构 | 如 Windows x64、Linux x64；协议端与客户端均须匹配 |
| 软件版本 | DSH、Node、QQ 插件或协议端、桥接、包管理器；保存锁文件或提交号 |
| 运行身份 | 专用操作系统用户、对应 home、DSH profile |
| 工作目录 | 新建的空目录或只有演示数据的目录 |
| 模型 | 当前账号实际可调用的 provider 与 model |
| 允许访问者 | 自己的测试账号；群聊另列测试群 |
| 验证记录 | 时间、测试消息标记、接收日志、DSH 会话、QQ 回执 |

通用配置原则：

1. 使用独立测试环境，先让 DSH 本身能正常回答，再接 QQ。
2. 先设置访问控制，再开放消息处理。名单未配置时保持关闭；首次身份采集只在受控测试范围内进行。
3. `cwd`、运行目录和实际可访问文件范围分别检查。设置工作目录不自动保证目录外不可读。
4. 用实际工具权限限制文件、命令与网络能力。提示词中的“不要访问其他文件”不构成权限隔离。
5. 初次只开放必要能力；需要审批的操作应能回传审批或明确拒绝，不能静默等待，也不能一律关掉审批。
6. 凭据不进入教程附件、Git、聊天截图或共享同步目录。二维码、登录态、Cookie 和管理令牌同样按凭据处理。

## 3. R1 · DSH–个人 QQ 小号本地接入

### 3.1 组件与选型

```text
测试者的 QQ → 机器人小号 → QQ 客户端 / 协议端
                              ↕ OneBot
                           DSH 桥接
                              ↕ 本地接口
                             DSH → 模型
```

本轮实际组件：Windows x64、QQ 9.9.36-53644、Node 24.21.0、NapCat Shell v4.18.41、DSH 0.2.1-rc.2。代码、安装锁文件、启动/检查脚本与脱敏验证记录位于 [qq-personal-lab](../README.md)。NapCat 包已核对 SHA-256，QQ登录和 DSH模型调用分别通过；事件入站和QQ回复以真实私聊记录为准。

版本应成套锁定。检查当日 `qq-bridge` 的包声明要求 Node ≥ 22.13.0；SnowLuma 当前文档对 Lite 发行包要求 Node 24+。完整发行包与 Lite 包的运行时要求不能混抄。[桥接包声明](https://github.com/Derpyu520/qq-bridge/blob/main/package.json)、[SnowLuma 发行说明](https://github.com/SnowLuma/SnowLuma#快速开始)。

### 3.2 实施顺序

1. **准备 DSH**：用专用测试 profile 启动，验证模型可用，确认本地服务地址及鉴权方式。
2. **准备小号与协议端**：按所选协议端文档安装匹配的 QQ 客户端/运行组件，由账号持有人完成扫码或登录确认。确认登录身份确实是小号。
3. **配置协议接口**：区分 OneBot WebSocket、HTTP API 与管理页面；只绑定本机地址，设置非空访问令牌。
4. **准备桥接**：在独立目录取得已选定版本，按其锁文件安装依赖，复制示例配置为本地私有配置。先审阅安装脚本的写入范围，再执行 DSH 侧安装步骤。
5. **配置最小行为**：只允许测试者私聊，群聊先关闭；关闭自主闲聊、角色扮演、自动研究、历史学习和主动发言等业务扩展。不要删除桥接所必需的协议规则或受限工具预设。
6. **接通两侧**：分别填 DSH 地址/鉴权和 OneBot 地址/令牌；使用与所选版本匹配的普通聊天模式。确认 QQ 消息进入 DSH，再确认回复返回小号的会话。
7. **验收后记录**：保存脱敏配置、版本、启动方式和停止方式。退出协议端登录前，先停止桥接，避免残留发送任务。

本轮最小桥接使用独立 `DSH_HOME`，预设 `qq-lab-chat` 没有 MCP 或角色业务模块。通过工具注册表限制与执行 guard 实际禁用工具，并记录零工具证明。完整复现命令见 [实验仓库说明](../README.md)。原始上游安装器包含额外仿真行为，不作为本方案安装前置。

### 3.2.1 本机实际步骤与踩坑

1. 检测宿主 QQ 的进程和安装路径，使用已有 QQ.exe 启动独立 NapCat 实验实例。沙箱看不到宿主进程时，需在授权宿主上下文复核。
2. 遇到“当前账号已登录，无法重复登录”：用户仅退出原客户端的小号，再调用 QuickLogin。此次复用本机缓存成功，不代表新机免扫码。
3. HTTP 13000、WS 13001、管理页16099、DSH13080全部绑定127.0.0.1，令牌随机生成并忽略入库。
4. 旧版 DSH API 客户端独立安装在 `vendor/`。与新版 DSH 混装会造成作用域模块多份、预设重复注册；拆分并去重后加载正常。
5. Windows 自定义插件路径必须生成 `file:///` URL，普通盘符路径曾导致 `never started`。
6. 复用已有 DeepSeek 账号时只导入必要账号记录到隔离 home，选择 `deepseek-account / deepseek-flash`，不复制人格、职务、项目文件与旧会话。固定模型测试已通过。
7. 主号在好友私聊中发送一次性配对口令，然后直接发送普通文本；`/dsh ` 为可选前缀。一次性配对已成功；2026-10-27 23:01（北京时间）已补处理真实消息并得到QQ发送回执、历史回复。仍待下一条新消息验证实时监听。

### 3.3 R1 验收

- 允许的测试账号发带唯一标记的消息，收到一次对应回复。
- 未允许账号的消息被访问控制拦截，且没有创建模型轮次；不能只凭“没回复”判断拦截成功。
- 两个独立会话不会串上下文，机器人自己的回复不会重新触发自身。
- 小号退出登录后，桥接能显示账号离线；重新登录后恢复，不补发不应发送的旧任务。
- 停止桥接后，小号不再自动回复。

## 4. R4 · DSH–个人 QQ 小号上云部署

这条路线迁移的是**完整个人号链路**。如果 DSH 在云端、QQ 协议端仍在家中电脑，电脑关机后仍会断链，不能称为完成独立上云。

已找回历史服务器并通过SSH只读预检：Linux x86_64、Node22、约2GiB内存，可用约637MiB；已有官方Bot及另一个QQ号的NapCat/AstrBot容器。不能覆盖现有实例。部署资源与端口审计详见 [云端预检](云端预检.md)。

### 4.1 上云前的适配核对

| 核对项 | 通过条件 |
|---|---|
| 操作系统和 CPU | QQ 客户端、协议端原生组件、桥接、DSH 均有适配版本 |
| 图形环境 | 所选发行方式是否依赖桌面会话、显示服务或特定容器运行条件已查明 |
| 运行权限 | 使用普通服务用户，已确认该用户能访问所需客户端、状态目录和 DSH 鉴权材料 |
| 网络 | 服务器能访问 QQ 与模型服务；管理端口不直接向公网开放 |
| 登录恢复 | 明确状态保存位置、失效识别、重新扫码入口及负责人 |
| 组件许可 | 自托管、自动部署、镜像打包和再分发的范围已核对 |

SnowLuma 文档提供 Linux 启动入口，但这不能单独证明任意无桌面云主机均可运行完整链路。还需验证 QQ 客户端、原生组件与发行包条件。[SnowLuma 文档](https://github.com/SnowLuma/SnowLuma#快速开始)。

若选 SnowLuma，其 EULA §5.4 对包含专有组件的自动化部署、第三方安装包或 Docker 镜像有书面授权要求。因此本指南提供架构与验收，不把它擅自封装成可分发的一键云安装包。[SnowLuma EULA](https://github.com/SnowLuma/SnowLuma/blob/main/EULA.md)。

### 4.2 推荐部署结构

先采用同机部署，减少跨机器鉴权与暴露端口：

```text
云服务器
├─ QQ 客户端 / 协议端：维护小号登录与收发
├─ DSH：独立运行身份、模型凭据、受限工作目录
└─ DSH 桥接：连接以上两者，维护会话映射与访问控制

管理电脑 ── SSH 隧道 ── 云端管理页
```

同机进程之间使用回环地址；若分容器运行，改用受控容器网络，容器内的 `127.0.0.1` 不能代表另一容器。管理页面通过 SSH 隧道访问，OneBot API 不因上云而直接公开。

### 4.3 施工与切换

1. **云端预检**：核对系统、架构、磁盘、内存、网络和所需运行组件。不要沿用官方 Bot 的内存测量值给个人号链路定规格。
2. **部署 DSH 与桥接**：使用独立运行用户，按云端实际 home 重建 DSH 鉴权与路径。Windows 启动器、盘符和缓存目录不能直接搬到 Linux。
3. **准备协议端**：按许可与发行文档完成云端安装；验证管理页面可经隧道访问。账号尚未登录时先完成其他检查。
4. **停止本地自动处理**：停止桥接并暂停旧任务；按协议端要求退出或关闭旧实例。保存回退配置。
5. **在云端登录小号**：完成扫码或设备确认。优先在新设备建立登录态；不假定复制旧会话文件一定有效，不通过循环登录绕过验证。
6. **连接并验证**：确认协议端能收到真实消息、桥接能投递 DSH、DSH 能产生回复、QQ 能收到该回复。
7. **建立托管**：给 DSH、桥接及协议端分别确定启动/停止与重启方式。Linux 可使用 systemd 或所选发行方式的进程管理；先确认协议端是否依赖桌面会话，再写服务。
8. **验证恢复**：测试桥接重启、DSH 重启、网络中断与整机重启。依赖服务“进程已启动”不等于“消息已可用”，需重试与就绪检查。

不要把安装成功自动等同于允许切换生产小号。可以先用另一个测试账号演练云端环境，再安排目标小号的短时切换。

### 4.4 状态迁移清单

| 内容 | 迁移方式 |
|---|---|
| 访问白名单、连接配置 | 脱敏配置模板迁移，云端重新填秘密值 |
| 模型凭据、OneBot 令牌、管理密码 | 在目标环境独立配置，不打进发布包 |
| DSH 鉴权材料 | 按桥接支持方式在目标环境建立；不复制整份个人 DSH home |
| QQ 登录态 | 使用协议端支持的恢复方式；不兼容或失效就重新扫码 |
| 会话映射 | 默认新建；若保留，必须保证目标 DSH 中对应会话存在且权限正确 |
| 未完成任务与待发消息 | 切换前处理或清空，避免迁移后重复执行 |
| 人格、业务资料、历史聊天 | 最小接入不迁移 |

### 4.5 R4 追加验收

- 本地电脑关机后，QQ 小号仍能完成一次真实对话，云端日志对应同一标记。
- 整机重启后重新验收真实消息，不只检查服务是否 `enabled`。
- 检查账号在线状态和收消息健康度；WebSocket 心跳存活不代表 QQ 入站正常。
- 登录态失效能被识别并提示重新登录，不无限重启刷登录。
- 回退时先停云端桥接和账号实例，再恢复本地；确认只有目标实例处理消息。

## 5. R2 · DSH–官方 QQ Bot 本地接入

### 5.1 接入方式

使用 `@tencent-connect/dsh-qqbot`。桌面端当前文档支持在插件页安装，再到设置中的 QQ 机器人入口扫码绑定。CLI 则安装到指定 profile 后启动。扫码得到的是官方 Bot 接入凭据，不是个人小号登录态。[官方插件说明](https://github.com/tencent-connect/dsh-qqbot)。

CLI 路线可使用以下上游基本命令；正式复用时应换成已验证的固定版本，避免每次拉取不同依赖：

```bash
npx @deepseek-ai/dsh plugin --profile qqbot add @tencent-connect/dsh-qqbot
npx @deepseek-ai/dsh --profile qqbot
```

桌面端由应用管理 profile；不要拿“CLI 无法改 desktop profile”推导“桌面端不能接官方插件”。独立 CLI profile 是便于隔离与迁移的一种选择。

### 5.2 配置与凭据

1. 在 DSH 内先验证模型，再安装并绑定官方插件。
2. 根据当前账号入口完成 Bot 创建、测试用户配置及凭据获取。不能把一次实测的后台流程视为所有主体均相同。
3. 设置专用工作目录；只开放测试用户私聊，群聊保持关闭。
4. 尚未取得 user openid 时，保持受控测试范围，可在禁用处理且开启必要诊断的状态下采集身份；核对具体版本日志是否提供所需字段。
5. 填入非空私聊白名单，再进行回复验收。

配置要点如下。这是字段清单，需合入当前版本完整配置，**不是可覆盖整份 profile 的成品 YAML**：

```yaml
access:
  c2cMode: allowlist
  c2cAllow: ["<测试用户的 user openid>"]
  groupMode: disabled
  groupAllow: []
```

官方插件当前源码会把空允许名单转换为 `['*']`，因此启用 `allowlist` 时不能留下空名单。不做群聊时明确 `disabled`，避免只收紧私聊却遗留群聊入口。[访问控制装配源码](https://github.com/tencent-connect/dsh-qqbot/blob/main/src/gateway/middleware-setup.ts)。

`directPrompt` / `groupPrompt` 是可选的场景提示词，不要求填角色或职务；删除旧业务提示词后仍应保留实际权限控制。首次只验证普通文本，不加入全量群记录补丁。

### 5.3 R2 验收

- 用插件支持的探活命令验证通道，再用自然语言验证模型；两者不能互相替代。
- 允许用户收到回复，名单外用户有拦截证据且没有进入模型。
- 重启后绑定与访问设置保留，实际生效目录正确。
- 测试错误信息和工具结果是否泄露私有路径或凭据。

## 6. R3 · DSH–官方 QQ Bot 上云部署

### 6.1 云端重建的内容

| 项目 | 云端处理 |
|---|---|
| Node、DSH、插件 | 按已验证版本重装，保留锁文件；不复制 Windows 的 node_modules |
| profile | 使用专用用户的 profile，重写系统路径 |
| 模型 | 核对 provider、可用 model、凭据来源 |
| Bot 凭据 | 通过受限文件或秘密管理服务注入 |
| 访问控制 | 保留同 Bot 的已验证名单；换 Bot 后重新取得并验证 openid |
| 进程管理 | 固定启动程序绝对路径、用户、工作目录、日志和重启策略 |
| 审批 | 选择可执行的审批/拒绝策略，不将 `never` 作为聊天接入硬要求 |

检查当日官方插件源码版本为 0.5.3，包声明要求 Node ≥ 20.3.0；这证明旧稿“Node ≥ 18 即可”的通用要求已不可靠。最终以所选 DSH 与插件组合的共同要求为准，源码分支版本不等于已安装版本。[插件包声明](https://github.com/tencent-connect/dsh-qqbot/blob/main/package.json)。

### 6.2 凭据注入

原工程所用插件的环境变量为 `QQBOT_APPID`、`QQBOT_SECRET`；采用相应模型适配器时另配置模型密钥。环境文件只存放在服务器受限路径，公开示例只保留空字段名。

对本轮核对的插件源码，`__FROM_ENV__` 会触发环境变量读取；普通字符串 `${QQBOT_APPID}` 不会在该函数内被插值。若仍保留旧的非空明文配置，可能优先使用旧值，应清理重复来源。[环境变量解析源码](https://github.com/tencent-connect/dsh-qqbot/blob/main/src/shared/utils.ts)。

使用 systemd 的 `EnvironmentFile` 时，明确文件属主与权限：`root:root` 的 0600 文件由系统服务管理器读取，并不等于普通运行用户能直接读取该文件。凭据数量正确也不代表值有效，还需验证实际鉴权。

### 6.3 网络与切换

1. 检查实际部署插件使用的连接方式。对原工程的出站长连接模式，不需要为 QQ 回调暴露 Web 服务；后台若启用 IP 白名单，应填写实际公网出口 IP。
2. 本机 IP 仅在需要本地调试或回退且平台要求时加入，不把“两条 IP”写成所有人的硬要求。
3. 云端先完成离线安装、配置检查和网络检查，先不与生产 Bot 建立第二个处理实例。
4. 停本地实例，确认退出，再启动云端实例。
5. 使用唯一标记的 QQ 消息完成云端端到端验收；失败则停云端、恢复本地。
6. 验收成功后再启用长期托管、监测与备份。接受短时维护窗口，不用同 Bot 双活来冒充无缝迁移。

### 6.4 R3 追加验收

- 服务运行、通道连接、模型回复、访问控制四项分别通过。
- 本地停止后仍可回复，云端日志能对应测试消息。
- 实际重启服务器后再次完成真实消息验收。
- 回滚配置仍可用；若轮换了凭据，同步更新回退方案。

## 7. 群聊是场景扩展，四条路线均单独验收

先完成私聊，再增加一个测试群。明确允许群、触发条件、发送频率和错误回显方式。

普通“被 @ 后回答”不应默认附带全量群消息采集、群档案、日志双向同步或三处自定义代码补丁。只有明确需要这些功能时才启用，并单独记录授权、数据保存位置和保留期限。

群聊至少测试：允许群内 @ 能回复；普通消息与 @全体按设定不误触发；未允许群不进入模型；不会回复自身；长回复受控；多成员的工具权限不会互相继承。按群共享上下文不等于按成员隔离文件权限。

官方 Bot 的群能力还受当前平台授权和事件模式约束；不要将旧工程中“必须开启获取全部消息”的设置推广到所有 Bot。

## 8. 可复用迁移包只包含什么

| 包含 | 不包含 |
|---|---|
| 版本清单、来源链接、锁文件 | 真实 AppSecret、API Key、OneBot token、Cookie、登录态 |
| 无秘密值的配置模板 | 个人角色设定、职务、项目知识库、聊天记录 |
| 经验证的启动/停止/健康检查说明 | 全量 DSH home、个人默认 profile、浏览器状态 |
| 服务配置模板和工作目录说明 | Windows 缓存、跨平台 node_modules |
| 验收记录、回滚步骤 | 原工程压缩包或自解压安装脚本的未经审查副本 |

旧工程的 `install-qqbot.sh` 和 `qqbot-deploy.tar.gz` 含非空凭据字段，不能直接用于复用交付；其部署脚本也与本指南的新口径不一致。详细证据见配套《清洗与审计记录》。

## 9. 排障顺序

| 症状 | 优先检查 |
|---|---|
| 收不到 QQ 消息 | QQ 身份是否在线 → 协议端/官方通道是否收事件 → 白名单是否拦截 |
| 收到事件但无 DSH 会话 | 桥接鉴权、字段/版本兼容、preset 是否安装、队列状态 |
| DSH 有会话但无模型回复 | provider、model、凭据、余额、超时或待审批状态 |
| DSH 已回复但 QQ 未收到 | 发送权限、事件关联、去重序号、文本长度、平台返回码 |
| 偶发重复或串会话 | 多实例、自身回声、事件去重、会话映射和旧任务重放 |
| 重启后失败 | 运行用户/home、路径、秘密文件读取、登录态、服务就绪顺序 |
| 管理页和 WS 正常但没消息 | 个人号登录与接收链路健康度，不能只看端口存活 |
| 环境迁移后工具越界或拒绝 | 操作系统权限、实际沙箱模式、会话 cwd、继承的工具配置 |

回复频控应按平台、消息场景和消息 ID 理解。旧稿把“每条入站消息的回复窗口/次数”简化成“每小时最多对话四次”，应删除。当前可访问的腾讯文档镜像还同时含主动消息停用说明和旧额度表，因此本指南不固定宣传“每月四条主动消息可兜底”。实际以部署时官方说明、应用权限和接口返回为准。[腾讯消息发送文档](https://github.com/tencent-connect/bot-docs/blob/main/docs/develop/api-v2/server-inter/message/send-receive/send.md)。
