## 2. 已确认、影响复用的主要问题

优先级：P0 表示旧材料不能直接进入共享安装包；P1 表示可能导致接入失败或权限错误；P2 表示表述或证据不足。

### P0-1：安装载荷内嵌了凭据字段

`install-qqbot.sh` 的自解压载荷和 `qqbot-deploy.tar.gz` 都包含 `deploy-qqbot.sh` 与 `qqbot.env`。在内存中解码并读取后，确认环境文件中的 `QQBOT_APPID`、`QQBOT_SECRET`、`DEEPSEEK_API_KEY` 均非空，且未表现为明显占位文本。

本轮没有打印或转存这些值，没有验证它们当前是否有效。两个载荷中的部署脚本一致，且与同目录脚本一致。证据摘要只保留成员名、哈希和布尔检查结果，见《审计证据摘要.json》。

**处理**：新指南不再引导运行或分享旧安装包，公开配置只提供字段模板。如果旧载荷曾共享给不应持有凭据的人，需要轮换对应密钥；本轮未自行轮换，以免中断既有服务。

### P1-1：部署脚本与指南不一致

静态证据：`deploy-qqbot.sh` 223—233 行生成 IM 配置，其中 appId/appSecret 使用字面量 `${...}`，没有 `c2cMode`、`c2cAllow`，还保留记录员业务提示词。两个安装载荷内的脚本也有同样问题。

上游当前 `resolveEnv` 并不解析这种普通字符串插值。插件访问模式的默认值又是开放，因此“旧包执行成功”不能等同于“已正确绑定且只允许自己使用”。[解析源码](https://github.com/tencent-connect/dsh-qqbot/blob/main/src/shared/utils.ts)、[插件配置说明](https://github.com/tencent-connect/dsh-qqbot#配置项)。

**处理**：新指南明确字段来源、非空名单和首次关闭策略。旧脚本未在本轮修复或重新打包，仍不能作为新指南附件直接执行。

### P1-2：体检可能输出秘密值，且验收指标不足

`check-qqbot.sh` 217—220 行原样打印 patch 与 service。即使环境文件只显示键名，扫码保存的 patch 仍可能带明文 AppSecret。原文“体检不回显密钥”的保证不成立。

原检查还把凭据项数、历史就绪日志、服务状态当作完成度指标；这些都不能代替真实收发与拒绝测试。

**处理**：新指南改为分层验收。未来脚本需按字段白名单生成脱敏摘要，加入新鲜时间窗、模型回复、名单外拦截和实际重启测试。

### P1-3：云端切换顺序前后冲突

原指南 53 行及 723 行提示双实例问题，但 853 行又要求“上云验证通过再停本机”。这会让相同 Bot 在验证阶段被两个实例同时处理，无法可靠归因。

**处理**：先完成不接生产身份的云端预检，随后停旧、启新、用唯一消息标记验收；失败时停新、启旧。个人号上云还需处理 QQ 登录态与待发队列。新指南不把“单 AppID 只能一个连接”扩写成未经核验的平台全局硬限制，而将单处理实例作为本工程的部署约束。

### P1-4：将工作目录误写为完整权限边界

原文 480 行将 `process.cwd()` 注释为可读写边界，589 行又写“只能读写这个目录”。工作目录、可写根、可读范围与工具能力不是同一个概念；提示词也不能提供系统级隔离。

**处理**：保留专用目录，同时要求验证操作系统与沙箱的实际访问范围、会话 cwd 和工具权限。删除“提示词硬约束保证安全”“workspace-write 保证目录外不可读”的暗示。

### P1-5：群聊业务功能被误当成接入要求

原文把开全量消息、全量落盘、三处 node_modules 补丁列为群聊必做。它们服务于旧项目的群记录需求，不是所有群聊机器人的必要条件。

**处理**：通用主线只做受控收发。群聊、全量收集、持久化、同步分别追加；不复制旧业务补丁。

### P1-6：个人号上云必须补齐协议端和登录态

新增 R4 后，不能只搬 DSH 或换成 Linux systemd 就宣称完成上云。QQ 客户端/协议端、桥接、DSH 都要在目标环境适配；管理页面在线也不能证明 QQ 接收链路正常。

**处理**：主文增加完整链路、系统适配、登录恢复、状态迁移和关本机验收。SnowLuma 文档虽提供 Linux 入口，完整个人号云端组合仍需实测。[SnowLuma 文档](https://github.com/SnowLuma/SnowLuma#快速开始)。

## 3. 已修正的技术口径

| 旧说法 | 新口径与依据 |
|---|---|
| “Node ≥ 18”即可 | 上游 Bot 插件包声明 ≥20.3.0；个人号参考桥接 ≥22.13.0；SnowLuma Lite 当前说明为 24+。按组合核对，不混成一个最低值 |
| “必须独立 CLI profile，desktop 不能装” | CLI 对托管 profile 的限制不等于桌面 UI 不支持安装。当前官方插件 README 有桌面安装与扫码路径 |
| “所有配置变动必须重启” | 旧版经验不能泛化；当前插件绑定路径有热重载逻辑。迁移仍需核实实际生效与旧会话状态 |
| “空 `[]` 会导致 YAML 解析错误” | `[]` 本身是合法 YAML；问题是未配置、格式拼接错误或加载语义。检查解析与合成结果，不以字符或条目数量判定 |
| “审批必须 never” | 纯聊天无需把所有工具免审批；应选择可交互审批或拒绝，并验证无静默挂起 |
| “每小时只能聊四次” | 回复限制按关联消息与场景理解，不能等同于对话轮次。具体数字暂不作为教程保证 |
| “主动消息每月四条可自动兜底” | 可访问腾讯镜像同时有停用通知和旧表格；当前能力需要应用权限与实际响应确认 |
| “IP 白名单必须两条” | 按当前实际出口与回退需要配置；不能把个案数量作为验收条件 |
| “enabled 就证明重启恢复” | enabled 只证明配置了自启，必须真实重启后测试消息 |
| “轮换后第三方 root 就看不到密钥” | 轮换不能剥夺宿主机管理员对新凭据的读取能力；这取决于宿主信任与部署边界 |
| “`.stignore` 保证私密资料永不回流” | 排除同步不证明未通过旧副本、日志、备份或模型调用外流；主线不搬业务资料 |
| “Windows 只能放弃沙箱或彻底不可用” | 降级为旧版本/旧环境故障记录，不作为跨版本事实，不把全权限作为通用修复 |
| “开自动续费是交付硬要求” | 改为记录续费/停机安排；自动扣款是部署者的预算选择 |

来源：以上运行时要求见 [Bot package.json](https://github.com/tencent-connect/dsh-qqbot/blob/main/package.json)、[桥接 package.json](https://github.com/Derpyu520/qq-bridge/blob/main/package.json)、[SnowLuma README](https://github.com/SnowLuma/SnowLuma)。热重载见 [插件入口](https://github.com/tencent-connect/dsh-qqbot/blob/main/src/index.ts)，消息规则冲突见 [腾讯文档镜像](https://github.com/tencent-connect/bot-docs/blob/main/docs/develop/api-v2/server-inter/message/send-receive/send.md)。
